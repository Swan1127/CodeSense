# 引导式学习平台并发承载评估设计

## 1. 目的与证据边界

本评估用于确定 CodeSense 引导式学习功能在智谱模型作为唯一大模型服务的条件下，能够稳定承载的并发请求规模，并定位瓶颈来自平台进程、数据库、网络还是智谱接口。

评估结果可作为论文中的系统性能与部署可行性证据，包括响应延迟、吞吐量、错误率、限流率和资源占用。它不能证明三阶段框架提升了真实学生的学习成绩，也不能替代虚拟学生驱动的基线与消融实验。

## 2. 被测链路

测试覆盖两条链路，并分别报告结果。

### 2.1 智谱上游链路

通过项目现有的智谱客户端发送与引导式学习长度相近的请求，测量模型服务在不同并发水平下的响应时间、429/1305 限流、重试和失败情况。该测试用于识别上游服务阈值，不包含 Gunicorn、Flask 路由和数据库开销。

### 2.2 平台完整链路

从服务器本机通过 HTTP 请求线上平台，使用专门的测试账号、测试班级和测试作业调用真实引导式学习接口。测试至少覆盖一个短响应接口和一个典型长响应接口，优先选择阶段一提示与阶段三对话。该链路包含 Nginx、Gunicorn、Flask、会话验证、数据库读写以及智谱调用。

测试数据必须带有统一的研究压测标识，与真实学生课程数据隔离。清理测试数据时仅允许按该标识删除，不得使用宽泛条件。

## 3. 方案选择

采用分层阶梯压测，而不直接进行高并发线上冲击。

1. 先运行单请求基线，确认账号、接口、日志和指标采集正常。
2. 对智谱上游链路进行阶梯测试，得到限流与延迟曲线。
3. 对平台完整链路进行同样的阶梯测试，比较两条曲线并定位平台额外开销。
4. 仅在服务器低峰期执行完整链路测试；达到停止条件后不再提高并发。

这种设计兼顾真实性和可诊断性。只压智谱无法评价平台，只压完整平台又难以判断故障来源。

## 4. 负载模型

### 4.1 并发阶梯

默认并发水平为：1、2、4、8、16、24、32。

每档先发送 20 个有效请求。前一档未触发停止条件时才进入下一档。测试脚本允许通过参数减少单档请求数或限制最高并发，但不得自动突破 32 并发。

### 4.2 请求构成

上游链路使用固定提示词模板和固定长度区间，避免因为输入规模变化造成结果不可比。完整链路采用两类请求：

- 短交互：阶段一或阶段二提示，请求和输出相对短；
- 长交互：阶段三教师或学生智能体对话，包含较长上下文。

两类请求分别测试，不在同一轮中随机混合。完成单类型曲线后，可增加一轮接近课堂行为的混合负载，默认短交互占 60%，长交互占 40%。混合比例属于工程场景假设，不解释为真实课堂分布。

### 4.3 重复与预热

每条链路在正式测试前执行 3 次串行预热。正式测试至少重复 3 轮，轮次之间保留冷却时间。论文报告各轮合并结果和轮间波动，不选择性保留表现最好的一轮。

## 5. 停止与保护条件

任一条件满足后，当前链路停止提高并发，并保存已经产生的结果：

- 当前档总错误率超过 5%；
- 智谱 429 或 1305 限流比例超过 10%；
- P95 端到端响应时间超过 60 秒；
- 出现 502、504、Gunicorn worker timeout 或服务不可用；
- 服务器 CPU 或内存持续接近饱和；默认阈值为连续 30 秒超过 90%；
- 管理员人工中止。

单个请求最长等待 120 秒。测试脚本必须支持 Ctrl+C 安全停止，并在中止时写出已完成请求的结果。

## 6. 指标与记录格式

每个请求记录以下字段：

- 测试编号、轮次、链路、请求类型和目标并发；
- 开始时间、结束时间和端到端耗时；
- HTTP 状态码或智谱错误码；
- 是否成功、是否限流、是否重试及重试次数；
- 输入和输出字符数或 token 数（能够可靠取得时）；
- 响应中的模型名称；
- 错误类别，不保存密钥和认证凭据。

每档汇总以下指标：

- 有效吞吐量，单位为成功请求数/秒；
- 成功率、错误率和限流率；
- 平均响应时间、P50、P95 和 P99；
- 重试比例和平均重试次数；
- CPU、内存、Gunicorn worker 状态及数据库连接情况；
- 502、504、超时、连接失败和业务错误的数量。

原始结果使用 JSONL 保存，汇总结果使用 CSV 保存，另生成适合论文使用的延迟—并发、吞吐量—并发和错误率—并发图。所有结果均保留测试时间、模型名称和服务器配置快照。

## 7. 瓶颈判定

通过两条链路的差异判断主要瓶颈：

- 两条链路在相近并发水平同时出现限流或延迟突增：主要瓶颈在智谱上游；
- 上游链路稳定而完整链路恶化：检查同步 Gunicorn worker、数据库连接、Nginx 超时和平台资源；
- 完整链路吞吐量在 worker 数附近停止增长，同时排队延迟上升：同步 worker 被长时间模型调用占用；
- 资源占用不高但出现大量 502/504：检查代理和应用超时配置；
- 错误集中在会话或业务校验：属于测试账号、CSRF 或状态准备问题，不计入容量上限，修复测试夹具后重测。

当前生产配置采用同步 Gunicorn worker，超时时间为 120 秒。模型调用期间 worker 会持续被占用，因此平台完整链路的并发能力预计与实际 worker 数和智谱响应时间密切相关。该判断属于待验证假设，不能预先写成实验结论。

## 8. 安全与数据隔离

- 测试仅在低峰时段执行，并提前确认没有课程活动；
- 只使用专门创建的测试账号、测试班级、测试作业和测试会话；
- API 密钥、Cookie、密码和完整认证头不得写入结果文件；
- 默认从服务器本机访问平台，避免将公网网络波动混入主要结果；
- 首次线上测试最高并发限制为 8，确认无异常后才允许执行完整阶梯；
- 脚本不得修改真实学生记录，不得通过全表删除方式清理数据；
- 测试结束后检查应用错误日志、worker 状态和平台可用性。

## 9. 实现边界

后续实现应新增独立压测脚本和结果目录，不把压测逻辑放入线上业务路由。脚本至少提供 `upstream` 和 `platform` 两种模式，支持并发阶梯、每档请求数、最高并发、请求超时、冷却时间和输出目录参数。

平台模式需要显式提供测试账号和测试作业标识。若无法安全建立独立测试数据，平台模式不得运行，只能完成上游测试和本地仿真。

实现时需要为统计聚合、停止条件、凭据脱敏和中断落盘编写自动化测试。真实智谱调用和线上负载不进入常规测试套件，必须由显式命令触发。

## 10. 论文中的使用方式

论文应把本实验命名为“系统并发与稳定性评估”或“部署性能评估”。结果用于回答以下问题：

1. 在当前服务器和智谱模型配置下，平台在哪个并发范围内保持可接受的成功率与响应时间？
2. 性能拐点主要由智谱限流还是平台部署结构造成？
3. 三阶段中的短交互与长交互是否表现出不同的容量边界？

论文不能根据该实验声称框架提高学习效果，也不能把最大并发数描述为脱离服务器配置和测试日期的固定系统能力。报告必须注明模型、服务器、worker 数量、测试时间、请求构成和停止规则。

## 11. 验收标准

设计实施完成后，应满足以下条件：

- 能够在不修改业务代码的情况下分别运行上游和平台链路测试；
- 能从并发 1 开始自动阶梯上升，并在触发停止条件时停止；
- 中断或部分失败时仍能保留完整的已完成请求记录；
- 输出原始 JSONL、汇总 CSV、配置快照和三类论文图表；
- 输出中不含密钥、密码、Cookie 或完整认证头；
- 能根据两条链路的结果形成可复核的瓶颈判断；
- 论文表述严格限定为性能与部署证据。
