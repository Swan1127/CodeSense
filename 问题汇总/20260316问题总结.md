gemini总结：
1. 教师仪表盘内容重构 (对应原问题1)
我们发现，当前教师仪表盘处于内容真空状态，缺乏辅助教学决策的数据支撑，与学生端的丰富度形成巨大落差。

可以考虑采用数据可视化看板的方案解决。前端需开发专属的图表组件（如引入 ECharts），聚合后端统计的班级整体表现（如作业完成率分布）和学生个体进度数据进行直观展示，将该页面打造为教师的数据决策中枢。

2. 角色视图隔离与权限字典对齐 (对应原问题2、3、5)
我们发现，系统存在严重的越权UI展示与路由错位问题。教师界面不仅混入了学生的“重新提交”等无逻辑操作，且大量教师可见的按钮（如班级对比、同步数据、学生详情）被后端的管理员鉴权拦截，点击后进入死胡同。

可以考虑采用基于 RBAC（基于角色的访问控制）的视图深度隔离重构来彻底解决。前端必须根据当前用户角色上下文（Context/Store）动态渲染组件，精准隐藏无权操作的按钮并修正返回路由；后端需重新梳理并开放接口权限，赋予教师查看其负责班级和学生详情的必要权限。

3. 数据格式化显示修复 (对应原问题4)
我们发现，在渲染班级信息时，页面出现了诸如“2023级级”的文本叠字异常，影响系统专业度。

可以考虑直接清理后端数据库中的脏数据，并审查前端 Jinja2 模板（或 JS 渲染逻辑）及后端数据组装层，移除硬编码的冗余“级”字后缀，确保字符串的精确拼接。

4. 落地智能作业生成功能 (对应原问题6)
我们发现，teacher/add 页面预期的“智能格式化作业”核心能力缺失，教师仍深陷手动编排作业格式的低效劳动中。

可以考虑采用我们前期设计的“AI 辅助结构化生成流程”解决。在前端保留输入入口，后端接入 LLM API，通过定制化 Prompt 将教师的自然语言或杂乱粘贴内容，自动解析并拆分为问题描述、公开示例以及隐藏测试用例，并将其预填入我们的标准表单中供老师一键发布。

5. 引入动态沙箱评判流水线 (对应原问题7)
我们发现，当前的代码评估过度依赖大模型的静态/语义分析，由于缺乏基于测试用例的动态执行验证（OJ功能），我们无法获得 100% 确切的代码运行正确性结论。

可以考虑采用引入多阶段沙箱评判流水线的方案解决。在后端评估链路中，前置集成一个轻量级的安全沙盒环境（如基于 Docker 的评测机），自动拉取作业的私有测试用例执行学生提交的代码。将其标准输出的匹配度（客观对错）与大模型的代码质量评价（主观好坏）整合，生成最终的综合评估报告。
